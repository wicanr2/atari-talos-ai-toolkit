# 142 — IKBD 的相對滑鼠上行封包

狀態：**CONFORMED**。

## 範圍

本切片做 IKBD **往主機方向**的相對滑鼠位置封包：主機端把一次滑鼠移動與按鍵狀態
交給機器，IKBD 依門檻決定要不要發封包，三個位元組經 ACIA 依序送進 RDR，
每一個都設 RDRF、拉 MFP channel 6 的中斷，由 ROM 自己讀走。

**不在本切片**：鍵盤 make／break 掃描碼、joystick、絕對滑鼠模式、
`$07` 的 button-as-key（`mss=100`）與 absolute report 兩個位元、
門檻不等於 1 的情形、ACIA overrun（RDRF 還沒被讀走就來下一個位元組）、
以及主機下行命令（那是規格 138）。

## 證據

- **已確認（Atari IKBD 協定文件，兩份獨立來源逐字相同）**：相對滑鼠位置紀錄是
  三個位元組——

  ```text
  %111110xy   ; mouse position record flag
              ; where y is the right button state
              ; and x is the left button state
  X           ; delta x as twos complement integer
  Y           ; delta y as twos complement integer
  ```

  <https://www.kernel.org/doc/Documentation/input/atarikbd.txt> 與
  <https://www.atari-wiki.com/index.php?title=Keyboard_Protocol>。
  依這個位元佈局，**左鍵是 bit 1、右鍵是 bit 0**：`$F8` 都沒按、`$F9` 只有右鍵、
  `$FA` 只有左鍵、`$FB` 兩個都按。
  > 分歧留痕：搜尋引擎的摘要把 `$F9` 說成左鍵。那與上面兩份原文的位元佈局相反，
  > 本規格以原文為準。要推翻這條，得拿出比位元佈局更直接的一手證據。
- **已確認（同上）**：封包在「任一軸的移動量超過門檻」時非同步產生；
  依 mouse key mode，按鍵按下或放開也可能產生封包。門檻由 `$0B` 設定，
  RESET 後預設為 1，且**只影響何時發封包，不影響送給主機的解析度**。
- **已確認（同上）**：`$10 SET Y=0 AT TOP` 是預設值，「朝向使用者的移動為正、
  遠離為負」；`$0F SET Y=0 AT BOTTOM` 反過來。
- **已確認（規格 138，本專案）**：EmuTOS 1.3 開機時送出 `$08`（相對回報）、
  `$0B 01 01`（兩軸門檻都是 1）、`$10`（Y 原點在上）、`$07 00`（button action 0）。
  所以開機路徑上要處理的就是**門檻 1、Y 原點在上**這一組。
- **已確認（本專案既有模型）**：ACIA 一個位元組佔 10 個位元時間，
  一個位元時間是 1024 個機器 clock（讀時鐘回應那條路已經在用 `10 × 1024`）。
  投遞時設 RDR、`ikbdACIAStatus |= $81`、`mfpGPIPIn &^= $10`、`mfpIPRB |= $40`。

## typed 行為

1. 主機端把一次滑鼠事件交給機器：兩軸的相對位移與左右鍵狀態。
   位移累加到兩個累加器上，按鍵狀態直接覆蓋。
2. **門檻只接受 1**（`$0B 01 01`，EmuTOS 設的值）。任一軸的門檻不是 1 時，
   收到滑鼠事件一律**失敗即關閉**——「超過門檻」在門檻大於 1 時是 `>` 還是 `>=`
   兩份文件都沒寫死，本切片不猜。
3. 門檻 1 之下：任一軸的累加量不為零，或按鍵狀態有變化，就產生一個封包。
   封包取出累加量並歸零；單一位元組裝不下的量（超出 `-128..127`）
   **失敗即關閉**，本切片不做拆封包。
4. 封包三個位元組依序排進上行佇列：`$F8 | 左<<1 | 右`、delta x、delta y，
   兩個 delta 都是二補數。`$10`（Y 原點在上）之下，delta y 直接送累加量；
   `$0F` 不在本切片，設過 `$0F` 之後收到滑鼠事件失敗即關閉。
5. 佇列每 `10 × 1024` 個 clock 送出一個位元組，且**只在 RDRF 為 0 時送**。
   到了時間而 RDRF 還是 1，代表主機沒跟上——那是 overrun，不在本切片，
   失敗即關閉。
6. 主機從 `$FFFC02` 讀走上行位元組時，走既有的 RDRF 清除與 GPIP 還原，
   但**不**落進「reset 回應／stale RDR」那條分支。
7. 佇列滿（超過兩個封包）時再收滑鼠事件，失敗即關閉。
8. cold reset 清掉佇列、累加器與按鍵狀態。

## 驗收

- synthetic：四種按鍵組合的表頭值、負位移的二補數、Y 原點在上時 delta y 的符號、
  門檻不是 1 時 fail-closed、累加量超出一個位元組時 fail-closed、
  三個位元組的投遞間隔與 RDRF／GPIP4／IPRB 效果、RDRF 未清時 fail-closed、
  佇列滿 fail-closed、cold reset 清空。
- 固定 ROM：開機到桌面（規格 140 的 14,000,000 條錨點）之後注入一次已知的滑鼠
  移動，跑過數個 VBL，**畫面上的游標要正好位移相同的像素數與方向**。
  游標位置以「與桌面基準畫面相異像素的外接矩形」定位，不依賴任何 ROM 版本專屬的
  變數位址。
- 完整 CPU 語料、全測試、vet 與 build 通過才升 CONFORMED。

## 停止線

- 不宣稱 IKBD 已建模：鍵盤、joystick、絕對模式、button-as-key 與 overrun 都還沒做。
- 不宣稱按鍵的**語意**（哪一顆是 GEM 的選取鍵）已驗——本切片只驗表頭的位元位置
  依文件排對。要驗語意得做點擊測試，那需要按鍵按下與放開兩個封包，另開切片。

## CONFORMED 收據

- 2026-09-06：synthetic 通過——六種封包（四種按鍵組合的表頭 `$F8`／`$F9`／`$FA`／
  `$FB`、負位移的二補數 `$FF`／`$80`、兩軸上界 `$7F`）逐位元組正確且每一個都設
  RDRF、拉低 GPIP4、設 IPRB bit 6；沒位移也沒按鍵變化不發封包；送出後累加器歸零；
  門檻不是 1、Y 原點在下、非相對模式、位移 128／−129、佇列滿、RDRF 未清全部
  fail-closed；cold reset 清乾淨。
- **固定 ROM 的 oracle 是 EmuTOS 自己的 VDI**：開機到桌面（規格 140 的 14,000,000
  條錨點）之後注入已知的移動，量畫面上游標的位移。桌面剛畫完時箭頭是 **10×16**、
  左上角在 **(159,99)**，所以位移 `(dx,dy)` 必須讓「與基準相異像素的外接矩形」
  變成 `(10+|dx|)×(16+|dy|)`：
  - `(+30,0)` → 40×16
  - `(0,+40)` → 10×56
  - `(+20,+10)` → 30×26

  每一次移回原點之後，畫面與基準**逐像素相同**（相異像素 0 個），
  所以位移量沒有被加速或縮放。
- **方向由畫面邊界釘死**：連續往負方向推 400 像素，變動框左上角貼到 `x=0`；
  往正方向推 800 像素，右下角貼到 `(319,199)`。負是左／上、正是右／下
  （`$10` Y 原點在上之下，delta y 為正就是往下）。這條不依賴任何 ROM 版本專屬的
  變數位址。
- **順帶修掉一個模型自身的缺陷**：CPU 在 `STOP` 時原本直接跳到下一個 VBL
  （一次 157,426 clocks），三個位元組會在同一次裝置推進裡全擠出來，主機一個都
  來不及讀。真硬體上 ACIA 中斷會把 `STOP` 叫醒，所以 idle 跳躍現在會停在
  上行位元組的投遞時刻。這個缺陷在只有下行命令時看不出來——ROM 那時是主動輪詢的。
- 完整 CPU 語料、EmuTOS 端到端、UCSD 那一組、vet 與 build 全數通過。
